工程与架构

Picord 是如何构建的。

一个 Node.js 进程、一个 SQLite 文件、无构建步骤的 Web 前端。Pi Durable 驱动 agent,并在任何人看到之前提交每一步。Picord 在其上加了频道、账号与人,以及手机。本页讲清:组成部分、一条消息如何穿行其间、以及保持一致的规则。

TypeScript,无构建 Preact + htm 经 Pi Durable 的 SQLite Node.js 22.19+

架构

组成部分。

浏览器通过 JSON API 和事件流与唯一的服务进程对话。服务把状态存在 Pi Durable 的存储里,启动时从它重建其余一切。浏览器看到的大多数内容都已落库;少数活跃状态只存内存:谁在线、谁在输入、等待批准的调用、内置浏览器的页面。

room.ts

房间

每个被观看的会话一个房间。90 毫秒批量聚合变更,把条目压成紧凑 JSON,只给每个标签页发送它还缺的条目与字段。

commands.ts

命令

人向 Pi 提出的一切,都先校验角色、邀请范围与轮流发言。他人应知晓的变更,会成为会话聊天里的活动行。

app.ts

唯一的提交监听

唯一能听到每一次提交的地方:记录作者、标记忙碌会话、统计花费、更新房间。功能对提交作出反应,而不是轮询。

store.js

事件流

默认服务器推送事件。当隧道拖慢了流,应用切到长轮询并记住一天。

reload.ts

热重载

被修改的扩展重新导入并以同名安装。运行中的工具调用在旧代码上收尾;加载失败的模块保留上一个可用版本。

projection.ts

小更新

长工具输出与文件内容在实时视图里裁剪展示。有人展开时,标签页再请求完整条目。

请求路径

一条消息,从头到尾。

从手机上点下发送,到每个打开的标签页都看到 Pi 的回答,中间发生了什么。

  1. web/composer.js

    带着 id 发出

    标签页把消息 POST 到 /api/c/:id/submit,并带上自生成的 id——网络错误后重发也不会发两次。

  2. commands.ts

    先校验,再入队

    角色、邀请范围、轮流发言与花费限额逐一校验,提示词模板展开。消息带着 u:<人>:<id> 的请求 id 进入会话收件箱——它同时说明是谁写的。Pi 工作时,消息加入当前运行或作为后续排队。

  3. pi-durable

    作为持久任务运行

    模型请求与每个工具调用都是边走边提交的任务。计划模式、Lancet Guard 与目标检查钩进这些任务。

  4. app.ts

    只被听到一次

    提交监听器看到每次提交:记录作者、标记会话忙碌、统计花费,并通知正在观看该会话的房间。

  5. room.ts

    以变更发出

    房间最多等 90 毫秒聚合变更,然后经事件流把每个标签页缺的部分发过去。

  6. web/store.js

    渲染

    store 应用更新,Preact 渲染。重连的标签页会重新拿到完整视图,因此每台设备看到一致的内容。

持久化

崩溃之后依然成立的规则。

Pi Durable 提供任务、检查点与原子提交。Picord 用它们保证:任何时刻重启,都不改变任何人能看到的东西。

先提交,再显示

存下来才可见

浏览器只渲染已提交的状态。Picord 的文档与聊天记录在同一批提交里变更,崩溃后两者不会互相矛盾。

request id

只发一次

每条发给 Pi 的消息都带请求 id,同时说明是谁的工作。重试发送、 ! 命令、定时消息、监视消息在重启后重发,都会找到已存在的那一条。

memo

只问一次

钩子把结果存进任务的 memo:一次批准的答复、一次目标的检查。重启后钩子重新运行,读 memo 而不再询问或检查。

replay: "safe"

只在无害时重跑

被重启切断的工具调用,只在重跑无害时再次运行——如 artifacts、定时、记忆与 PiP 的工具。否则模型会被告知"已被中断",并自行检查实际发生了什么。人运行的 ! 命令绝不运行两次。

持久任务

跨过重启的时间

定时消息是 harness 里休眠的任务。休眠中重启,继续休眠;超过时限后重启,立即发送且只发一次。

fork 策略

分叉即数据

每个文档声明分叉时是复制还是留空。分叉的初始化在同一批提交里修剪复制来的内容,比如置顶与作者,裁剪到分叉点。

状态

万物归位。

Picord 的文档与 Pi Durable 自身的(聊天记录、agent 设置、收件箱、运行视图、用量)并存于 pocket.sqlite。它们的类型就是存储的数据,因此永不变名。

扩展

功能即扩展。

Picord 加在 agent 周围的许多能力,都是 Pi Durable 扩展:工具、钩子、提示词段落与任务定义,按此顺序安装。编辑一个,运行中的服务即时重装。

  1. prompt.ts段落

    系统提示词:面向手机屏幕的准则、项目的 AGENTS.md 文件、Pi 的技能、工作目录。以及本 fork 的规矩:问早期细节先调 search_history,跨频道交接用 channel_post。始终开启。

  2. channels.ts工具

    本 fork 新增:channel_post 让 Pi 把消息推进另一个频道,对方频道的 Pi 在其频道内读取并回答。

  3. history.ts工具

    本 fork 新增:search_history 检索原始条目(本会话/全部会话/指定会话),治长对话压缩摘要的"跨天失忆"。

  4. session-cleanup.ts 路由 · 浏览器面板

    采纳自上游 0.30:所有者对归档会话"移除并清理"(移出应用并清理 worktree/上传/日志,转录保留在 durable 存储),支持批量与年龄过滤。

  5. artifacts.ts工具

    带版本的 HTML、Markdown、SVG 产物,在沙箱中打开。

  6. browser.ts工具 · 段落

    Pi 与会话中的人共享的真实浏览器:带元素引用的快照、点击、输入、截图、控制台。计划模式下只许看。

  7. subagents.ts工具 · 任务

    后台子代理。每个由一个锚任务持有;每个回答由一个报告任务带回父会话。

  8. schedules.ts工具 · 任务

    定时消息,以及 Pi 为自己安排后续的工具(频道的总结倒计时由此驱动)。

  9. goals.ts钩子 · 段落

    每次最终回答后运行会话的完成检查,未通过则让 Pi 继续推进。

  10. plan.ts钩子 · 段落

    计划模式:会改变内容的调用在运行前被拦下。

  11. guard.ts钩子

    Lancet Guard:高风险 bash、write、edit 调用等待人工批准。默认关闭。

  12. codemode.ts工具

    以脚本调用其他工具。每次调用经过与直接调用相同的钩子。

  13. memory.ts工具 · 段落

    Pi 跨会话保留的经验。Pi 用其工具提议;段落列出该会话项目已批准的经验。

  14. pip.ts工具 · 段落 · 任务

    PiP 的工具、提示词,以及会话运行结束时的跟随报告任务。只有 PiP 自己的会话选择它。

  15. triggers.ts工具 · 任务

    PR 与仓库监视,以及 Pi 的 watch_pr 工具。webhook 需要它开启。

本 fork 移除了上游的 pocket-relay(外部聊天平台中继:Discord、Slack、Telegram、Matrix、RSS、HTTP),不接任何聊天平台。 所有者自己的模块在 ~/.picord/extensions/ 中,在这些之后加载,默认关闭,经 node_modules 链接导入相同的包。

PiP 与触发器

跨越会话的工作。

PiP、监视与 webhook 以某个人的身份行动,带着那个人的校验与花费限额。与记忆一样,各自把需要的东西存进存储,重启后继续。

pip.ts

PiP 的会话

标记为 PiP 专用、从一切会话列表中隐去的会话。它选择自己的扩展(没有 bash、write、edit)。只有其所有者可见,其工具以与所有者相同的命令行动。

pocket.pip-follows

跟随

跟随是持久任务,在会话运行结束时向 PiP 报告。PiP 发出的消息带以其工具调用生成的请求 id,重放的调用既不重发也不重复跟随。

watches.ts

监视

监视是持久任务,休眠到下一次查看,经 gh 询问 GitHub,发送前把要告诉 Pi 的内容存进检查点。发送的请求 id 由任务与计数构成,重启后只发一次。

hooks.ts

Webhook

/hook/… 在 /api 及其登录之外。携带该 hook 的密钥才能进入;GitHub 的请求则以密钥签名校验。带来的内容经标签围栏 (fence.ts),作为数据交给 Pi。

memory.ts

记忆

全应用一份文档。项目按 git 公共文件夹为键,仓库与其 worktree 共享经验。Pi 或访客保存的经验,等所有者批准其看到的文本后生效。

model-names.ts

谁来选模型

只有人选。子代理运行在其会话的模型上,或所有者允许的模型。PiP 只在其所有者指名时才传递模型:在其消息里,或在其设置的监视/webhook 里。

安全

窄入口。

Pi 以启动服务的人的身份运行命令,因此应用严格限制谁能提出请求,以及页面与回复能做什么。

  • 登录。 随机令牌哈希存储于 HttpOnly、SameSite=Lax 的 Cookie。本 fork 新增账号密码登录与邀请码注册;未登录一律重定向到登录页。默认严格私有隔离:每人只见自己的会话与主动共享的群组。
  • 请求。 /api 之下任何会改变内容的请求,必须携带 X-Pocket 头,其他站点的表单无法伪造。Webhook 走 /hook/…,以各自的密钥校验。
  • 页面。 应用不从其他站点加载任何东西:策略只允许自身文件与哈希过的内联脚本。回复经净化,artifacts 在与应用隔离的沙箱中运行。
  • 浏览器。 页面在服务器的 Chromium 中运行,对人只以图像呈现,永不接触应用。使用需转向权限,文件属所有者,打开的每个地址都会显示在聊天里。
  • 角色。 所有者、转向、只读,可作用于全部会话或单个会话。Lancet Guard 的批准可要求由非请求者答复。
  • 来自外部。 Webhook 与监视以设置者的身份行动。GitHub 的 issue、PR 与评论,只统计有仓库写权限的人,除非设置者选择任何人。
!

转向即 shell 权限。 能转向的人就能让 Pi 在这台机器上运行命令。worktree 让会话文件彼此分开,花费限额能停掉运行——但都不是沙箱。SECURITY.md 详述受保护的范围。

实践

为改动而生。

Picord 常常被 Pi 从内部修改,所以代码必须保持易读、改动安全、运行时可变。

无构建

无需编译

Node 以剥离类型的方式运行服务端 TypeScript,因此只使用可擦除语法。前端是 Preact 与 htm 的原生 ES 模块。

依赖

少依赖

Earendil 的 Pi 系列包,锁定在测试过的版本;另有 Preact、htm、marked、DOMPurify、qrcode、undici 与 jiti。Web Push 内置。

npm test

在真实核心上测试

测试运行真实服务,配一个脚本化模型:真实 SQLite、真实 git 仓库,以重新打开同一数据目录模拟重启,定时测试把时钟拨快。前端的一部分在真实 Chromium 中测试。

npm run check

类型检查

TypeScript 编译器检查服务端与测试。前端文件每次编辑后做 Node 语法检查——一个坏文件会让所有打开的标签页白屏。

AGENTS.md

可热改

前端文件改动即时刷新到所有浏览器,扩展就地重装;其余改动从菜单触发重启,重启后运行中的工作继续。

docs/map.md

写给人看

每个模块开头声明它管什么,注释用平实的句子讲为什么,还有一份代码地图帮 agent 找路。
